# GitHub 与 Railway — v2.0 版本更新指南（初版）

目标
- 将项目从 v1.0 升级到 v2.0（统一工作台），确保安全、可回滚、可观测。
- 覆盖：分支/版本策略、迁移与部署步骤、环境变量、灰度与回滚、Checklist。

一、前置准备
- 明确变更范围
  - 前端：移除 v1.0 组件（TrendsSection 等）、统一路由 /workspace、统一 AnalysisState
  - 文档：重组目录（v2.0 核心文档 + archive/ 存档）
  - 数据与后端：接口兼容性评估、必要的 Schema 迁移（待补）
- 权限与安全
  - GitHub：分支保护、必需 Review、必需通过 CI
  - Railway：环境变量密钥从本地/测试环境完全剥离；使用变量面板设置
- 清单
  - 版本迁移脚本/SQL（如有，待补）
  - 环境变量一览（见下）
  - 回滚预案与演练记录（模板见下）

二、分支与版本策略
- 分支模型
  - main：稳定产线分支（仅经由 release/* 合并）
  - develop：日常集成
  - feature/*：功能分支
  - release/2.0.x：发布分支（冻结范围，只修缺陷与文档）
- 版本号与 Tag
  - 遵循 semver：2.0.0 为首发；修 Bug 以 2.0.x 递增
  - 合并到 main 后创建 Tag：v2.0.0
- GitHub Actions（建议）
  - 触发：push 到 release/* → 执行构建与测试；Tag → 触发部署到预生产/生产
  - 构建产物：前端静态包/容器镜像；后端镜像；版本元数据写入

三、环境变量与配置（示例，按项目实际补齐）
- 通用
  - NODE_ENV=production
  - API_BASE_URL=https://api.example.com（待补）
  - LOG_LEVEL=info
- LLM/第三方
  - OPENAI_API_KEY / 阿里/Qwen密钥（如用，Railway中设置）
  - MODEL_NAME=（如：Qwen2-7B-instruct 或 Llama3.x，本地/云端对齐）
- 数据/缓存
  - REDIS_URL=（如需）
  - DB_URL=（如需）
- 安全
  - CORS_ORIGINS=（前端域名）
  - SENTRY_DSN=（可选）
说明：所有密钥只在 Railway 仪表盘“Variables”中配置，Git 仓库不得提交明文。

四、GitHub 侧操作步骤
1) 创建发布分支
   - 从 develop 切出 release/2.0.0
2) 清理与合并变更
   - 移除 v1.0 组件与路由；统一到 /workspace
   - 重构统一状态 AnalysisState；修正引用与测试
   - 更新文档目录：v2.0-* 与 archive/
3) 完成 CI/CD
   - 单元/集成/E2E 测试通过
   - 构建前端/后端产物
4) 代码审查与安全检查
   - 至少 1-2 名 Reviewer
   - 依赖与许可证审计（待补工具链）
5) 合并至 main 并打 Tag
   - 合并策略：Squash/Rebase 任一；创建 Tag v2.0.0
6) 生成 Release Notes
   - 变更摘要、破坏性更改、迁移注意事项、回滚指南链接

五、Railway 部署步骤（零停机/低风险）
前提：已在 Railway 创建两个环境：Preview（预生产）与 Production（生产）。
1) 预生产环境部署
   - 通过 Tag/Release 触发部署至 Preview
   - 设置 Variables（见“环境变量与配置”），校验无硬编码密钥
   - 执行数据迁移脚本（如有，先演练可逆脚本）
   - 健康检查：/health, 日志、错误率、P95 延迟、页面巡检
2) 验证与灰度
   - 验收用例：关键用户路径（输入→分析→洞察→导出）
   - 指标门槛：错误率<1%、P95<1.5s（待补）、功能通过率≥95%
3) 生产环境灰度
   - 策略 A（推荐）：生产新建并行实例 v2.0，流量逐步放量 10%→50%→100%
   - 策略 B：蓝绿切换（blue=旧，green=新）；验证通过后切换路由
4) 切换与监控
   - 切换窗口：低峰期
   - 监控面板：错误率、延迟、资源、业务指标（报告导出、任务完成率）
   - 观察期：30-60 分钟；异常即回滚

六、回滚方案与演练
- 触发条件
  - 错误率/延迟超阈值，关键路径失败，数据异常
- 回滚步骤
  1) 流量回拨至旧版本/蓝环境
  2) 回滚应用版本：切回上一个稳定 Tag（如 v1.9.x 或 v1.0.x）
  3) 逆向数据库迁移（若不可逆，则需双写/影子表策略，提前设计）
  4) 清理新版本缓存与特性开关关闭
  5) 事故复盘与热修复计划
- 演练频率
  - 上线前进行一次完整演练；季度至少一次
- 回滚检查点
  - 链路拨测通过、数据校验、用户关键操作成功率恢复

九、常见问题（FAQ）
- Q：如何处理仍依赖旧接口的页面？
  - A：保留向后兼容层于短期，设定移除窗口；文档声明弃用计划
- Q：数据库迁移不可逆怎么办？
  - A：采用影子表/双写策略，验证后切换；不可逆操作延后到观察期后执行
- Q：如何在 Railway 上分环境？
  - A：使用多服务或多环境变量组；预生产与生产用不同变量集合与域名
